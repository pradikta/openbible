# ADR 0003: YES2 file format reference and parser boundary

- Status: Accepted as an implementation reference
- Date: 2026-11-04
- Source: [androidbible binary format documentation](https://github.com/yukuku/androidbible/blob/develop/docs/binary-formats.md)

## Context

OpenBible imports `.yes` and `.yes.gz` files produced for androidbible. The local parser currently assumes a section table made of a short string, offset, and size, and assumes verse records are `(ARI, string)` pairs. Those assumptions do not match the published YES2 description and must not be treated as a supported format specification.

## Verified YES2 structure

The signature is `98 58 0d 0a 00 5d e0 02`. The 32-bit section-index size occupies bytes 8–11. The index body begins at byte 12 with a one-byte index version (`1`) and a 32-bit section count. Each record stores a one-byte name length, name bytes, 32-bit relative offset, 32-bit attributes size, 32-bit content size, and four reserved bytes. The section data base is the position immediately after the index body. A section's attributes start at `dataBase + offset`; content starts after `attributes_size`. YES2 uses the names `versionInfo`, `booksInfo`, `text`, `xrefs`, `footnotes`, and `pericopes` (note the spelling). The file footer is documented as one byte `00`.

The index reader and top-level reader confirm this layout: [SectionIndex.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/model/SectionIndex.java) and [Yes2Reader.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/Yes2Reader.java).

`versionInfo` content is a Bintex VALUE Simple Map. Keys include `shortName`, `longName`, `description`, `locale`, `buildTime`, `book_count`, `hasPericopes`, and `textEncoding`; text encoding `1` means ASCII and `2` means UTF-8. See [VersionInfoSection.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/section/VersionInfoSection.java).

`booksInfo` content starts with a 32-bit book count, followed by Bintex VALUE Simple Maps. Each book map contains `bookId`, `shortName`, `offset`, `chapter_count`, `verse_counts`, and `chapter_offsets` (plus optional `abbreviation`). See [BooksInfoSection.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/section/BooksInfoSection.java) and [Yes2Book.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/model/Yes2Book.java).

The text data is not a stream of `(ARI, string)` records. For each chapter, seek to `book.offset + chapter_offsets[chapter - 1]`; then read exactly `verse_counts[chapter - 1]` verse records. Each record is a Bintex unsigned variable-length byte count followed by that many bytes of verse text, decoded according to `textEncoding`. Text attributes can specify `compression.name = "snappy-blocks"`; Snappy blocks support random access through their own block index. See [Yes2Reader.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/Yes2Reader.java) and [Yes2VerseTextDecoder.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/io/Yes2VerseTextDecoder.java).

The `pericopes` section has its own versioned compact index and variable-size blocks, not a simple `(ARI, title, strings)` table. Its reader accepts section data versions 2 and 3 and current blocks use version 4. See [PericopesSection.java](https://github.com/yukuku/androidbible/blob/develop/AlkitabYes2/src/main/java/yuku/alkitab/yes2/section/PericopesSection.java). Section attributes, metadata, and book records use Bintex maps; Bintex strings/arrays and raw text lengths must not be conflated.

## Decision

Treat upstream documentation and source code as the format authority. Keep parsing section-oriented and streaming where possible. Validate all offsets and lengths against the file/section bounds before seeking or allocating. Do not infer a section payload layout from a section name or from the current placeholder reader contract. Snappy support must decompress only the text section and must be managed/WASM-compatible.

Implement against the verified upstream layouts above and test with a minimal fixture generated by the upstream writer (or independently encoded to the same layout). Until a real fixture passes, the current parser is a scaffold and must not be described as fully YES2-compatible.

## Consequences

- Header, index, and payload parsing need to be corrected together; the existing `(ARI, string)` verse loop is not a verified YES2 layout.
- Section-name constants must match the upstream spellings; current local names are incompatible without an explicit alias policy.
- GZip input is non-seekable after decompression in the general case; seek-based section access needs a bounded spool or a different strategy that does not load an entire input file into memory.
- Fixtures and offline tests are required before claiming support for real-world YES2 files.
